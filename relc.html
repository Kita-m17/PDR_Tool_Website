Abstract

Abstract

Defeasible reasoning is a non-monotonic reasoning approach that allows the representation of exceptional information. We use the Kraus, Lehmann and Magidor framework, an extension of propositional logic, to perform defeasible reasoning. Understanding implicit inference from defeasible information is challenging because of the complex entailment algorithms. We propose a tool called PDR-Tool, an explanatory web debugger that lets users step through the algorithms that form part of the defeasible entailment process. By explaining the internal computations of the algorithms alongside the pseudocode definitions, we lower the barrier to entry for novices. PDR-Tool builds on prior work from previous projects and research in defeasible explainability. We discuss what the current tools for defeasible explanations offer and how we iterate on these systems. Given a knowledge base and query, we allow users to navigate the entailment process. We incorporated 4 entailment algorithms: Rational, Lexicographical, Basic and Minimal Relevant Closure. This paper focuses on Basic and Minimal Relevant Closure. We validate the system's correctness through unit tests based on worked examples in the literature. The system's faithfulness to the entailment algorithm definitions is informally evaluated by experts.

Introduction

Only remove what causes the conflict

Rational Closure removes whole ranks, so unrelated statements can be lost. Relevant Closure fixes this by first finding the statements that are actually responsible for the conflict (its justifications) and only removing those. Seeing only the final result doesn't show why a statement was removed, which makes the algorithm hard for beginners to follow.

Research question

To what extent can a step-through interface faithfully visualise and explain the internal computations of the Base Rank, relevance partition and Relevant Closure algorithms, and how efficient is this approach while maintaining correctness?

Methodology & contribution

Making Relevant Closure explainable

Basic and Minimal Relevant Closure were implemented to store their intermediate computations, so each page can step through them one iteration at a time with the matching pseudocode and an explanation. Justifications are found with Wang's hitting set tree rather than the full power set, which keeps explanations fast on larger knowledge bases. It builds on the components developed as a group, such as BaseRank and the shared step-through layout.

Justifications

The Partition page steps through sets of statements, tagging each as entailed and minimal, and explains whether it is a justification. Filters show all sets, only entailed sets, or only justifications.

Relevance partition

The justifications are combined into the relevant partition, and everything else, including the classical statements, forms the irrelevant partition.

Statement removal

The running knowledge base shrinks as relevant statements are removed rank by rank, with the sets before and after each removal. An entailed query comes with its smallest weak justification.

Comparison

Basic, Minimal and Rational

Basic Relevant Closure treats every statement in a justification as relevant. Minimal Relevant Closure only takes the lowest-ranked statement in each justification, so it removes the most defeasible information and keeps more specific information for the final check. Both remove less than Rational Closure.

Evaluation & results

Does it work?

The tool was evaluated on correctness, performance and informal expert feedback. A formal user study was outside the scope of the project.

Passing

Unit tests from the literature

JUnit tests based on worked examples from different research papers verify Base Rank, the relevance partition and Relevant Closure.

Consistent

Existing tools

Existing defeasible entailment tools were also used to verify the Base Rank, partition and Relevant Closure implementations.

Found an error

A fault in an existing tool

Testing revealed that klm-algorithms gave wrong Basic Relevant Closure answers in some cases. A manual work-through confirmed it, and the researcher was notified.

Power set → hitting set tree

Performance

Checking every set in the power set grows at 2N, which made Relevant Closure far slower than the other algorithms. Switching to the hitting set tree, which shows a sample of sets that still includes every justification, made it competitive.

Finding the partition still takes most of the time as knowledge bases grow, which is expected.

Expert feedback

Clear and faithful

Members of UCT's Knowledge Representation and Reasoning group found the explanations clear and faithful, and found no reasoning errors.

They suggested validating formulas as they're entered, so the input now checks formulas in real time with descriptive error messages.

Discussion & conclusion

What it shows

Key findings

  • The step-through leaves no guessing about why a statement is removed, or why a set isn't a justification.
  • Exposing the internal computations kept the answers correct.
  • The hitting set tree balances transparency with speed.

Limitations

  • No formal user study, so effects on learning are not measured.
  • The hitting set tree shows a sample of sets, not the full power set.
  • The free hosting tier slows the deployed tool down.

Future work

  • Strong justifications and minimal rank establishing sets.
  • Justification browsing, and justifications drawn as trees or graphs.
  • An AI assistant for exploring modified knowledge bases, grounded in the implemented algorithms.

Conclusion

This work presents a step-through debugger that visualises the Base Rank, relevance partition and Relevant Closure algorithms, with natural-language explanations at each step. Its correctness was verified against examples from the literature and existing tools, which also uncovered a fault in an existing implementation. Compared with existing interfaces, it gives a more detailed and faithful view of how Relevant Closure reaches its answer, making the algorithm easier for beginners to follow.
